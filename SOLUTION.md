# Решение: ручной табель сотрудников

Краткое описание исправлений, допущений и проверок. Условие задания - в [README.md](README.md).

## Как запустить

```text
dotnet build TimesheetCandidateTask.sln
dotnet test  TimesheetCandidateTask.sln

# терминал 1 - API (нужен для WPF)
dotnet run --project src/TimesheetCandidateTask.Api --launch-profile TimesheetCandidateTask.Api

# терминал 2 - WPF-клиент
dotnet run --project src/TimesheetCandidateTask.Wpf
```

## Причины наблюдаемых проблем и их исправление

| # | Симптом | Причина | Исправление |
| - | ------- | ------- | ----------- |
| 1 | «Добавить сотрудника» создаёт дубли | Локальное хранилище копировало первую строку с тем же `EmployeeId`; в API не было проверки уникальности | Уникальность сотрудника проверяется в `TimesheetService` (PUT -> 400, POST строки -> 409) и закреплена уникальным индексом `(TimesheetId, EmployeeId)`. Локальное хранилище заменено клиентом API; в UI кнопка добавляет ещё не добавленного сотрудника из справочника |
| 2 | Итог больше фактических часов | `TimesheetCalculator` прибавлял `holidayHours` к `workedHours`, который уже содержит праздничные часы | `TotalHours = WorkedHours` (праздничные часы входят в итог один раз, `HolidayHours` - отдельный показатель) |
| 3 | Комментарий попадает не в тот день; для 02.01 «не удалось обновить» | Поиск дня по `Date.AddDays(1)` в `TimesheetService` и в локальном хранилище WPF | День ищется по точной дате. WPF отправляет каждое изменение в «свой» день |

## Что сделано в API

- `GET`, `PUT`, `POST .../lines`, `PUT .../lines/{lineId}/comment` - согласованный контракт и описание кодов ответов в Swagger.
- Статусы: **400** (некорректный период/данные), **404** (нет табеля, строки или дня), **409** (табель утверждён, сотрудник уже в табеле, параллельное изменение).
- `Approved` блокирует PUT, добавление строки и изменение комментария.
- Ошибки превращает в HTTP-ответы один `TimesheetExceptionFilter` вместо повторяющихся `try/catch` в контроллере.
- Конкурентность: уникальные индексы `(RetailId, PeriodStart)` и `(TimesheetId, EmployeeId)`, токен `Version` на табеле
  (оптимистичная блокировка) и до трёх попыток операции при конфликте с параллельным запросом.
- PUT обновляет существующие строки по `EmployeeId`, поэтому `lineId` не меняется после сохранения.

## Допущения

- Строка сотрудника в табеле однозначно определяется `EmployeeId`.
- Период - всегда первый день месяца; все дни строки должны принадлежать месяцу табеля, даты дней в строке не повторяются.
- Часы дня - от 0 до 24; комментарий - не длиннее 1000 символов.
- `WorkedHours` - все фактически отработанные часы (дни `Workday` и `Holiday`), `HolidayHours` - их праздничная часть,
  `TotalHours` равен `WorkedHours`. Дни `Weekend` и `Absence` в итог не входят. В таблице WPF колонка «Будни» = рабочие минус праздничные,
  чтобы «Будни + Праздничные = Итого».
- `PUT` на несуществующий месяц создаёт табель (в том числе сразу утверждённый); `PUT` со статусом `Approved` утверждает черновик, после чего он неизменяем.
- Повторный `PUT` обновляет существующих сотрудников на месте, добавляет новых и удаляет отсутствующих в запросе.
- В демо-клиенте есть небольшой справочник из трёх сотрудников (в API справочника нет, по условию он не нужен).
  Когда все добавлены, кнопка сообщает об этом и дублей не создаёт.
- Неподдерживаемые условием вещи (авторизация, миграции, выгрузки, полный календарь) не добавлялись.
